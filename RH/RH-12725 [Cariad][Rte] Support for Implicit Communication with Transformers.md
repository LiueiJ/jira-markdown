## 描述

Summary:

This is a defect of RTE Code. Compile fails because of wrong RTE Code.

- **Background:** Cariad ** Customer’s SWC are using **Implicit** access point for SR ports to/from SomeIP signals. Previously customer were using RTA-CAR 9.1 with rba_SomeIpAdp for years. Now they migrate to RTA-CAR 12.6 without rba_SomeIpAdp. RTE doesn’t support this feature **Implicit+Transformer**. In hotline ticket ([RH-12725](https://rtahotline.etas.com/jira/browse/RH-12725)) a solution (add an adapter SWC again) is provided by Solution Team. But considering the complexity, only a temporary RTE code fix is done by CN team.
- **Root cause:**  RTE doesn’t support **Implicit+Transformer**.  (Detail analysis see: [Issue Analysis of RH-12725.docx!link_attachment_7.gif!](/jira/secure/attachment/173816/173816_Issue+Analysis+of+RH-12725.docx))
- **Impact of the problem:** Can’t satisfy customer requirement and software design. Even higher complexity of software and workflow of SOA solution. Acceptance of Cariad project can be difficult.
- **Mitigation Required (Propose Needs how to solve the problem):** RTE shall support feature Implicit+Transformer. RTE plugin on RTA-CAR 12.8 (the final version customer will use.) shall be provided.

> [!note]+ 2025-04-04 11:51 · [[Marc_Kaiser|Marc Kaiser]]
> Hello Yinchuan, 
>
>
>
> I have analyzed your issue in some detail. Here is what I found. 
>
>
>
> The code emitted by RTA-RTE for your configuration is indeed buggy and will not compile. That the extern declaration is uint8 and not uint8 [] is not the reason that this code is buggy. The C compiler is fairly forgiving when it comes to typing of external declarations. 
>
>
>
>
>
>  **When looked at the configuration I found that your RTE UseCase is this:** 
>
>
>
> LdCom Interface + SomeIpXf Data Transformation + Port Fan Out + Implicit Read Access (s)  
>
>
>
>
>
>  **Problems with the Generated RTE Code:** 
>
>
>
>  **Invalid direct assignment used for incompatible C types.** 
>
>
>
> This line should cause a Compiler Error because the left side of this assignment is a struct with 28 uint8 members and the right side is a uint8 [28] array. It is not a valid operation in C to have this direct assignment. A memcopy call would have been required. 
>
>
>
> ![[RH-12725-image004.png]] 
>
>
>
>
>
>  **Missing Inverse Transformation:** 
>
>
>
> For this InterEcu communication, there is a Data Transformation configured but the generated RTE code does not perform and Inverse Data Transformation. 
>
>
>
> ![[RH-12725-image006.png]] 
>
> ![[RH-12725-image005.png]]  
>
>
>
>
>
>  *Bug in RTA-RTE 12.6.0 vs Bug in RTA-RTE 12.5.0*: 
>
> Left side is 12.6.0. Right side is 12.5.0. 
>
>
>
> ![[RH-12725-image003.png]] 
>
>
>
> As you can see in RTA-RTE 12.5.0, it was even more buggy. Here the declaration of the buffer was missing completely. This code would also not compile.   
>
>
>
>
>
>  **Implicit Access to Inter ECU:** 
>
>
>
> RTA-RTE is actually supposed to abort RTE Generation with error for LdCom + Implicit Read/Write. This has been implemented with this ticket: 
>
>
>
>  **[https://jira.etas-dev.com/browse/RTE-7407](https://jira.etas-dev.com/browse/RTE-7407)** 
>
> ![[RH-12725-image007.png]] 
>
>
>
> It is not a common use case to have implicit read/write access to InterEcu signals. For TX direction, the implication of that configuration would actually be that the message is getting transmitted on bus after RE/Task termination. This is because implicit communication will synchronize task local and global buffer after RE/Task termination and for InterEcu, this means sending on bus. This is in almost all cases not what the user is trying to do so Implicit TX access to bus signal is very uncommon use case and is not supported by RTA-RTE. 
>
>
>
> Implicit RX access to bus signal makes more sense and could be what user is trying to do. But still this feature is not supported by RTA-RTE, currently. The tool is not capable of generating the required code. Instead it will generate uncompilable code in some scenarios and throw error while generating in other scenarios. Ideally it should always abort with error and never generate uncompilable code. 
>
>
>
>
>
>  **How to fix?** 
>
>
>
> We have to change the Use Case slightly in order for this to work. The parts that are not working together are Implicit Access and LdCom Interface. 
>
>
>
>  **LdCom Interface** + SomeIpXf + Port Fan Out +  **Implicit Read Access (s)** 
>
>
>
> We have to change it to: 
>
>
>
>  *{color:red} *Com*{color}*  **+ SomeIpXf** + Port Fan Out +  **Implicit Read Access (s)** 
>
>
>
> But it is highly unusual to use Com for SomeIp traffic. This is most likely not what you want. 
>
>
>
> Or: 
>
>
>
>  **LdCom Interface** + SomeIpXf + Port Fan Out +  *{color:red} *Explicit*{color} Read Access (s)* 
>
>
>
> This is more likely what you want but it required change to multiple SWCs, which you likely cannot do because SWCs might come from OEM. 
>
>
>
> There is a way to fix this without changing SWC. We could use Adder Adapter Plugin to let it generate an Adapter between the SWC(s) and the Inter Ecu Signal. Nothing would change for the SWCs and we would split the RTE UseCases into two: 
>
>
>
>  **UseCase 1:** 
>
>
>
> LdCom Interface + SomeIpXf + Explicit Read Access 
>
>
>
>  **UseCase 2:** 
>
>
>
> Explicit Write Access + Implicit Read Access 
>
>
>
>  *{color:#4EA72E} *Both of these Use Cases RTA-RTE can handle separately but RTA-RTE cannot handle it on a single communication graph.*{color}* 
>
>
>
> ![[RH-12725-image008.png]] 
>
> Adder Adapter is ready to be used. It is delivered to our one drive:  ![[RH-12725-image009.png]] CN-Solution <[https://bosch-my.sharepoint.com/shared?id=%2Fsites%2FVOSGlobalSolutions%2DHub%2DSync%2FShared%20Documents%2FETCN%2FCN%2DSolution&listurl=https%3A%2F%2Fbosch%2Esharepoint%2Ecom%2Fsites%2FVOSGlobalSolutions%2DHub%2DSync%2FShared%20Documents]> 
>
>
>
> You need to configure one small json (I can help) where you say which ports are to be adapted, then you generate Adder Adapter and it will integrate the Adapter into your System Extract/RTE cfg. It will even generate the Code for the Adder Adapter Runnable Entity. That code is very simple. It will basically only do: 
>
> IDT data; 
>
> Rte_Read_<>(&data); 
>
> Rte_Write_<>(&data); 
>
>
>
> So it is possible to get ASIL for that code fairly easily. 
>
>
>
> Downsides of this approach: 
> - There will be one more buffer and one more memcopy (performance) than would be optimal..
> - You get extra SWC for which you have to do Safety for (but its code is trivial). Also for SomeIP communication, usually the safety requirements are soft.
>
>
>
>
> But there is actually not really a good alternative for your UseCase that I can see. The only other way is to ask OEM to please change read access from implicit to explicit. 
>
