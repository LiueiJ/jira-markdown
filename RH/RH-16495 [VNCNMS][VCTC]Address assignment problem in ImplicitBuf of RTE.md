> [!note]+ 2026-06-30 14:36 · [[Marc_Kaiser|Marc Kaiser]]
> AI ANALYSIS (automated — verify before acting on this)
>
> Root Cause Confirmed: Type mismatch between implicit buffer and IOC composite type
>
> Christian's analysis is correct — this is a gap in the RTE-21019 fix. Here is the source-level evidence from the RTE generator:
>
> 1. The implicit buffer type (ISABufferInfo.cpp:TDBMemberType(), line 256-331) creates a struct with:
>
> struct Rte_DE_<type> {
>     <DataType>      value;    // always present (line 309)
>     Std_ReturnType  status;   // only if hasStatus (line 317)
> }
>
> 2. The transformer composite type (DataInstance.cpp:generateDataTransformerErrorCompositeType(), line 2070-2126) creates:
>
> struct {
>     Std_ReturnType    status;           // line 2112 (RTE-17104)
>     TransformerError  transformerError; // line 2121
>     <DataType>        data;             // line 2122
> }
>
> These two structs have different field order and different fields. The implicit buffer puts "value" first; the composite puts "status" first, adds "transformerError", and names the data field "data" instead of "value".
>
> 3. Why RTE-21019 only partially fixed this:
> The fix was applied to UnqueuedIOCDataChannel::getChannelType() (UnqueuedIOCDataChannel.cpp:159-208, line 170):
>
> if ( isXfrmInvUnqueuedDataCbkSet && connContainsXfrm && srDataInst->hasImplicitAccesses() )
> {
>     auto* wrappedType = compositeType->getElementDataType( compositeType->getElementIndex( "data" ) );
>     return *wrappedType;
> }
>
> This unwraps the composite type to just the raw data type when implicit + transformer are combined.
>
> However, XfrmQueuedIOCDataChannel::getChannelType() (XfrmQueuedIOCDataChannel.cpp:56-59) has NO such logic — it always returns the full composite type:
>
> TypeInfo& XfrmQueuedIOCDataChannel::getChannelType( void )
> {
>     return getUntransformedDataType(); // returns *_dataTransformerErrorType (full composite)
> }
>
> 4. Why --inter-ecu-no-ioc masks the problem:
> When this flag is set, IOC channels are not created for cross-core communication (see DataStoreConnection.cpp:381, 522). Without IOC, there is no type mismatch between the implicit buffer and a channel type — the implicit buffer data is used directly.
>
> 5. Field offset mismatch calculation:
> With the composite type, the IOC channel interprets bytes starting at offset 0 as "status" (Std_ReturnType, typically 1-4 bytes), then "transformerError", then "data". But the implicit buffer writes "value" (the actual data) starting at offset 0. This is exactly the misalignment observed: variable values shift by the combined size of status + transformerError, causing DriveTempSelectSt to appear where PsnTempSelectSt was expected.
>
> Suggested fix direction: Extend XfrmQueuedIOCDataChannel::getChannelType() with the same implicit-access-aware unwrapping logic present in UnqueuedIOCDataChannel::getChannelType() (line 170-181).
>

> [!note]+ 2026-06-29 08:15 · [[Christian_Fuerst|Christian Fuerst]]
> Hi [[Junsheng_ZHANG|Junsheng ZHANG]] .
>
> it seems that you have found a bug in the RTE generator, but needs confirmed by L3 (which I will forward the topic to L3).
>
> When SOME/IP transformers are used with implicit communication and cross-core IOC (without --inter-ecu-no-ioc), the generator creates a type mismatch between the implicit buffer entry (which contains only the raw data fields) and the IOC composite type (which wraps the data with status and transformerError fields). This offset difference causes the field misalignment you observed, where DriverTempSelectSt appears in the PsnTempSelectSt position.
>
> This is a variant of a known issue. Prior tickets RH-12725 and RH-11062 documented the basic implicit + transformer mismatch, which was partially fixed in RTA-RTE 12.9.1 (RTE-21019). 
> However, the IOC group path (triggered when --inter-ecu-no-ioc is not set) was not covered by that fix.
>
> Hope that helps for now until we got a response from L3.
