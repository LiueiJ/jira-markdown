## 描述

Hi Marc, 

I have a IpduM CodeGen issue. I’m using RTA-CAR 12.6. (But I got same issue after I migrate to RTA-CAR 12.7) 

In IpduM_InitValues, index of IpduM_TxSubParts_acst is generated incorrectly which causes Ecu reset because of IPduM buffer init writes data into irrelevant memory address. 

You see in first IpduM Dynamic part PDU, sub part id 44-119 are used. But in next PDU, id 87-108 are used. There’s incorrect overlap. 

![[RH-13446-image001.png]] 

![[RH-13446-image002.png]] 

When I look into BSW code gen script, I noticed in IpduM_Gen_Utils.ext, all ipduMTxDynamicSegment across all IpduMTxPathways are sorted by name….So the id of first ipduMTxDynamicSegment can be wrong. 

![[RH-13446-image003.png]] 

Is there any solution for this issue? Thank you very much for your support.

> [!note]+ 2025-07-16 14:48 · Marc Kaiser
> Hello Sisi,
>
> thank you for reporting this issue.
>  # In [IpduM_Gen_Utils.ext|, the dynamic segments are sorted by shortname:
>
> List[IpduMTxDynamicSegment] IpduM_getTxDynSubPartList(IpduMConfig this) :
>
> this.parent.IpduM_getipduMTxPathway() != null && this.parent.IpduM_getipduMTxPathway().size > 0 ?
>
> this.ipduMTxPathway.ipduMTxRequest.ipduMTxDynamicSegment.sortBy(e|e.shortName) : {}
>
> ;
>  # But in the generation of IpduM_InitValues, the sequence is determined by IpduM_getTxInitDynPartList() and it uses this code path:
>
> List[IpduMTxDynamicPart] IpduM_getTxInitDynPartList(IpduMConfig this) :
>
> let DynPartList = (List)(this.IpduM_getTxReqList().ipduMInitialDynamicPart) :
>
> DynPartList
>
> ;
>
> The difference is:
>  # IpduM_getTxDynSubPartList sorts by shortName
>  # IpduM_getTxInitDynPartList preserves the original order from the arxml. I think earlier this was the same on accident and there was no issue.
>
> The result is the behavior you have been observing. I have reported your issue with this ticket to product field: [https://jira.etas-dev.com/browse/BSW-28244]
>
> I have set the priority to high as it can only be discovered with runtime tests.
>
> I have created a small workaround in ConfGen that will make it so the sequence is the same between the two methods used. (It will only work until 9999 Segments..)
>
